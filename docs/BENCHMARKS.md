# Бенчмарк: монолит vs Python/Node-стек

Одинаковое железо, одна и та же Postgres (shared `pg-demo-db`/`pg-us-db`), одинаковые
57 тел запросов `/api/run`, снятые из HAR реального демо-дашборда
(line/bar/area/pie/table/pivot/geo). Нагрузка — 4 процесса × N потоков (клиент на Python,
GIL одного процесса исключён). Прогретый стек, 15–20 с на точку. Цель — **оверхед серверной
части**: база данных в обоих случаях одна и та же, её время входит в оба замера одинаково.

## Пропускная способность и латентность

| клиентов | Rust монолит, RPS | p50 | p95 | Python/Node стек, RPS | p50 | p95 | ускорение |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 8  | **233** | 20.9 ms | 98 ms  | 20.6 | 280 ms | 991 ms | **×11.3** |
| 16 | **291** | 37.9 ms | 139 ms | 27.5 | 532 ms | 906 ms | **×10.6** |
| 32 | **318** | 73.5 ms | 248 ms | 31.8 | 797 ms | 1762 ms | **×10.0** |

* у монолита ~3% ответов — ожидаемые `427` (два error-кейса из HAR: `ZERO_DIVISION`);
  остальные 200, как и у Python;
* Python-стек упирается в один Node-процесс `ui-api` (JS-пайплайн чартов) и в HTTP-хопы:
  `ui → ui-api → data-api (×N источников) → US`, каждый со своей валидацией JWT и
  JSON-сериализацией. У монолита один внешний HTTP-запрос и **нулевые сетевые хопы внутри
  процесса** (in-process роутеры, одна проверка токена на `/api/run`, общие типизированные
  структуры);
* цифры — про серверный оверхед, не про БД: база одна и та же, и её время входит в оба
  столбца. Без БД разрыв в пользу Rust был бы ещё больше (меньше CPU на JSON/JS).

## Память (docker stats / macOS footprint)

| компонент | Python/Node стек | Rust монолит |
|---|---:|---:|
| US | 97–131 MB | — |
| ui-api (charts engine) | 125 MB | — |
| data-api | 915–983 MB | — |
| control-api | 680 MB | — |
| meta-manager | 157 MB | — |
| auth | 183 MB | **3.3 MB** (auth-rs) |
| **серверная часть, сумма** | **~2.2 GB** | **~138 MB** (монолит 134 MB + auth 3.3 MB) |
| UI (общий образ) | 246 MB | 244 MB |
| Postgres | 264–424 MB | тот же |

Память Python-контейнеров включает page cache (docker stats); даже с этой поправкой разрыв
~10–16×. Монолит: холодный процесс ~26–50 MB, тёплый после трафика ~90–134 MB,
пик при 32–64 клиентах ~140–200 MB.

## Образы/артефакты (проверено по `docker images`)

| | Python/Node | Rust |
|---|---:|---:|
| us | `datalens-us:1.39.0` — **1.19 GB** | — |
| ui-api | `datalens-ui:0.3831.0` (`APP_MODE=api`, тот же образ, что UI) — **1.13 GB** | — |
| data-api | `datalens-data-api:0.2457.0` — **758 MB** | — |
| control-api | `datalens-control-api:0.2457.0` — **758 MB** | — |
| meta-manager | `datalens-meta-manager:0.52.0` — **1.15 GB** | — |
| auth | `datalens-auth:0.27.0` — **864 MB** | auth-rs бинарник **3.5 MB** (scratch ≈ 4.5 MB) |
| temporal | `datalens-temporal:1.27.2` — **616 MB** | не нужен (in-process очередь) |
| **серверные образы, сумма `docker images`** | **≈ 5.85 GB** (+616 MB temporal) | **≈ 24 MB** (monolith 18.1 MB + auth 3.5 MB) |
| из них реально на диске с учётом общих слоёв | ≈ 4.7 GB | ≈ 24 MB (scratch, слоёв нет) |
| образы, которые остаются в обоих вариантах | UI 1.13 GB + Postgres 795 MB | UI 1.13 GB + Postgres 795 MB |
| **deployment: уникальные образы** | **≈ 6.7 GB** | **≈ 1.95 GB** |

`docker images` показывает размер образа без дедупликации общих слоёв; `us`, `data-api`,
`control-api`, `auth` делят базовый слой 139 MB, поэтому уникальный объём меньше суммы.
Цифра «5.85 GB» — это сумма per-image размеров заменяемых серверных образов; на диске
освобождается ~4.7 GB (плюс 616 MB, если раньше стоял Temporal).

## Что это значит

* throughput: **~10×** при той же базе, на 8–32 клиентах; латентность p50 ниже в 13–20 раз;
* память серверной части: **~2.2 GB → ~138 MB** (≈16× меньше);
* артефакты: **~5.9 GB образов → ~24 MB** (scratch), число серверных контейнеров 6 → 2;
* из стека ушли Python, Node и Temporal: один статический бинарник на всё, UI остаётся
  официальным контейнером `datalens-ui`.

Ограничения замера: **Apple M4 (arm64, Docker Desktop, 8 vCPU VM)**, дефолтные воркеры
Python-стека, HAR-набор из демо-дашборда (~57 запросов), без тюнинга Postgres. Абсолютные
RPS зависят от железа; соотношение определяется устранением межсервисных HTTP-хопов,
V8/CPython-оверхеда и повторной валидации JWT. Локальные бинарники собраны под macOS
arm64; в поставке — исходники + Dockerfile'ы, образы собираются под архитектуру хоста
(x86_64 в том числе).
